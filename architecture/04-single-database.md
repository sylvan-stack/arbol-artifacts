# Architecture · 04 Single database and schema upgrades

Arbol uses one installed PostgreSQL database. Trunks keep their identities and independent Builds as the database changes. A breaking schema change ships with compatible Builds of the Trunks and other consumers it affects. The owner chose this architecture on 12 November 2026, accepted maintenance windows, and authorized an empty start after backing up the existing databases. The owner accepted ARC-4 as drafted on 12 November 2026 in ASD-1 of the Arbol Single Database Saga.

## File layout amendment

For [ARC-5](05-where-arbol-keeps-its-files.md), accepted on 17 November 2026, Arbol keeps nothing under `~/Library/Application Support/`. Its working state is in `~/.arbol/`, beside the settings, and its archival material on the external drive Mercury in `/Volumes/Mercury/Arbol/`. For this specification:

- The installation runtime directory is `~/.arbol/runtime/`.
- Build fit also checks the installation layout: a Build declares `installationLayout`, and a Build of another layout is refused at default and explicit start and at writer admission, as an incompatible schema is.
- Snapshots, restore receipts, release records and the prior release's signed App go only to `/Volumes/Mercury/Arbol/backups/`. A schema change and a snapshot restore refuse with `archive_unavailable` when Mercury's own volume is not mounted.
- "Retain or verify access to the payloads or reproducible inputs" is met by the recorded source revisions: older Builds are not kept as recovery payloads and are rebuilt from source when needed (ARC-D95). The prior release's signed App is the exception and is archived on Mercury (ARC-D96).

This amendment applies from the release that moves the installation, as [ARC-5](05-where-arbol-keeps-its-files.md) describes. The prior text, IDs and Decisions below keep their original scope.

## Session import amendment

For [IMP-0](../session-import/00-the-import.md), accepted on 18 November 2026, Arbol imports the saved sessions of Claude Code, Codex, Kimi Code, Pi and Mimo as read-only, archived chats. For this specification:

- *One installation and one migration authority*: migration revision 3 adds `chat_imports`, `exchange_imports` and an insert trigger on `exchanges`. It is additive under compatibility version 1 and is applied by the fenced procedure (IMP-0.11).
- *Build selection and release compatibility*: only a Build that reads or writes the new tables declares `minRevision: 3`; every other Build keeps its declaration, and an older `arbol` Build keeps working on revision 3 ([IMP-0 Builds that change](../session-import/00-the-import.md#builds-that-change), IMP-D14).
- *Maintenance and writer admission*: the importer is a writer. It checks the installed schema pair, takes one writer permit per session, stops with `maintenance` at draining or exclusive admission, and refuses a dry run under exclusive admission ([IMP-0 Admission, maintenance and failures](../session-import/00-the-import.md#admission-maintenance-and-failures), IMP-0.19). It is a writer exception of the chat tables and the only writer of the two provenance tables, as ARC-0's Session import amendment says.
- *Release records, verification and recovery*: the session import's raw archive on Mercury is not part of the database snapshots, so restoring an older snapshot can leave archive objects that no row names ([IMP-0 Known problems](../session-import/00-the-import.md#known-problems)).

This amendment applies from migration revision 3 and the `arbol` Build that declares `minRevision: 3`. The prior text, IDs and Decisions below keep their original scope.

## Scope

The installed database, schema changes and compatibility, Exchange drainage during maintenance, backup and recovery, the one-time clean start, and removal of Root identity from the running product. This specification replaces the operating model in [ARC-1](01-roots.md) and governs amendments to ARC-0/2/3, Builds, the Trunk runtime, the backend and Bridge, Driver chat identity, Subscriptions Vigor, the App and Forester integrations. The existing specifications retain their historical decisions and evidence.

## Behaviour

### One installation and one migration authority

The installed Arbol uses one configured PostgreSQL database, one private installation runtime directory and one backend endpoint. The installed database is the sole source of application data and schema state. Preserve local PostgreSQL, credential handling, owner-only endpoints and separation of component responsibilities (ARC-0). A test uses a disposable database and separate runtime directory. No launch or normal client can create, reset or migrate the live schema.

The Arbol database migration tool is the sole schema writer. It exposes the installed pair `{revision, compatibilityVersion}` to consumers through an installation-scoped schema read; the database migration ledger, not a file or Build manifest, is authoritative. The status read distinguishes unavailable, uninitialized and invalid/unknown history. Only explicitly authorized baseline initialization can create the ledger. A baseline has revision 1 and compatibility version 1. Each subsequent migration has the next immutable revision, the expected predecessor, an identity/checksum and its resulting compatibility version. Applying a migration must check the target and ledger, run the schema and data transformation and record its revision atomically in PostgreSQL. A migration that cannot honor this transaction boundary is outside the current procedure.

A requested upgrade applies the ordered prefix through its declared target. It refuses gaps, changed applied entries, an unknown or newer installed history and downgrades. A failed step leaves its predecessor as the last committed revision; earlier committed steps remain. No automatic reopening follows failure or a lost response. Retry from the verified ledger against the same release under the write fence, or use the recorded restore procedure. Re-running a completed target is a no-op. A normal upgrade preserves existing data under documented transformations. Destructive reinitialization is confined to the one-time transition below.

### Build selection and release compatibility

An additive migration advances `revision` and keeps `compatibilityVersion` only if every previously qualified consumer for that version still works. A breaking migration increments both. Build descriptions and immutable Build records declare `schemaCompatibility`, a nonempty array of unique positive integer `compatibilityVersion` values, each paired with a positive integer `minRevision`. For example: `"schemaCompatibility":[{"compatibilityVersion":1,"minRevision":3}]`. A database-dependent Build fits when the installed compatibility version matches and the installed revision is at least the declared minimum. The schema pair does not replace version checks for Bridge, Exchange files, Driver requests or other component protocols.

Trunk code names and Build numbering stay independent. A start with no Trunk specified uses `trivial`. The App can pass its current choice as an explicit Trunk code name. For the selected code name choose its newest working, runnable, compatible Build. An explicit runnable Build is used only if it fits (including an otherwise eligible explicitly runnable failed-check Build under BLD-0); never silently substitute. List the compatible runnable alternatives for that Trunk on `no_fit`. A Root-Contract-only or malformed Build cannot fit. Keep the normal distinctions for invalid input, unknown Trunk and unavailable schema. Retain the installed release's selected and in-use payloads, including any Build needed to settle an Exchange, under BLD-0 protection rules. No implicit default can select an unverified consumer across activation.

The shared launcher/runtime checks both default and explicit starts. The runtime checks again at writer admission, including when a packaged Trunk is invoked directly, against the same schema and admission generation used for the acceptance transaction. The backend checks its own compatibility before database-dependent work. A breaking release stages all affected installation consumers and their dependencies together: backend, runtime and applicable Trunks, as well as the matching App, renderer, Drivers and CLI where their interface changes. Before reopening, verify the intended working Build of each Trunk the installation exposes, including Trivial, and every required consumer. Incompatible older payloads may remain archived and must be refused on the live installation.

### Exchange lifecycle and persistence

One start identity is a caller-supplied Exchange UUID. Runtime resolves the Trunk and exact Build, starts the detached Trunk in its own process group, and returns the Trunk's acceptance or refusal. A successful acknowledgement follows both publication of its private Exchange folder and the acceptance transaction that records the chat, message, open Exchange and immutable `{trunk, build}` assignment. Use the same assignment in the folder, acknowledgement, database and rediscovery. A known refusal leaves no accepted work or Driver run. If the response is lost, look up the same UUID and recover its original receipt, including after completion and folder cleanup; while the start is unresolved report uncertainty or in-progress and keep the same ID. A retry must never start duplicate inference, repick a Build for an accepted Exchange, or replace its recorded input. Preserve the existing one-open-Exchange-per-chat guard, request lifetime, and the 15-second Trunk and 20-second runtime acknowledgement limits (RCT-2 and RTM-0).

App/backend restart, default selection changes and process exit do not change the assignment. Discover active and pending-settlement Exchanges by UUID from the installation's runtime directory, correlate with the saved chat record and expose the actual state after reconnect. Stop and answers target that UUID and its recorded process/control file, with process identity verified before sending signals. Preserve the existing normal stop, escalation, sleep-aware heartbeat and recovery behavior (ARC-3). Unknown/already ended stop is harmless. An ended process with a pending folder is still work to settle, even though no inference remains active.

Save the end to the folder first. Persist unsaved rows and the terminal state together, conditionally against the accepted open Exchange. Keep the folder until commit is confirmed or the matching terminal result is verified. If a process is gone, settle with its recorded compatible Build; use a different Build only if explicitly qualified for that recorded folder format and settlement semantics, and never change the original assignment. Save the recorded end if present, otherwise settle as interrupted. Preserve prior committed rows and the existing replaced-Exchange rules. Repeat settlement after a crash without duplicating rows or re-running the Driver. Report and retain an unprovable or incompatible pending result; it blocks migration rather than disappearing.

### Maintenance and writer admission

The installation runtime owns the shared admission contract; the migration tool controls transitions through it. One durable, installation-scoped state visible without querying the application schema governs every writer, survives process restarts and fails closed if unknown. Normal, draining and exclusive maintenance are distinct states; a release verification failure leaves the fence in place. A single maintenance owner changes state and checks the target. Admission, writer registration and exclusive acquisition are interlocked: no successful check may grant a write after the exclusive fence, including a queued request, direct executable, retained connection or worker resumed after restart. All write paths, including new listeners or tools, require that admission; deployment must disable pre-contract clients that could bypass it.

- **Normal:** starts, backend and listener mutations, periodic/manual Vigor writers and maintenance-safe settlement may enter. Admit before the first persistent effect and hold admission to the end of the operation. Cover direct CLI and Trunk starts and any raw SQL command, not just the Bridge.
- **Draining:** refuse new Exchanges and ordinary writes with `maintenance`, without consuming a Draft, replaying a mutation, changing settings or storing a paste. Pause listeners that originate write work, scheduled refresh and pruning/cleanup that could alter recovery inputs. Existing bounded operations admitted before the transition may finish; for an admitted start, establish its durable acceptance before draining it or establish that it left no work. Existing accepted Exchanges can continue to write; allow targeted answers, stops and settlement (including stuck recovery) under controlled admission. Read-only status and safe reads may continue; suppress implicit mutations such as read-triggered Draft reconciliation. Driver account reads and account cache refresh may continue if confined to independent Driver state.
- **Exclusive:** fence all normal and controlled writers, including stop/answer writes, after confirming there are no in-flight write permits, unresolved starts, active Exchanges, open Exchange rows or pending results. Ordinary database reads are suspended while schema stability is uncertain; migration/status and isolated verification are the only exceptions. Hold the fence through snapshot, migration, verification and any recovery. An interrupted operator command must not release it automatically.

This procedure uses the same short write fence before any schema-changing release, including additive migrations, so the recovery point includes every committed write. For a long healthy Exchange, wait or reschedule and reopen the unchanged verified release; use normal explicit stop and existing stuck recovery when applicable. A stopped but unsettled Exchange, unavailable database, unreadable pending folder or unaccounted writer blocks exclusive acquisition. Do not force a healthy Exchange or discard pending data just to make a window.

### Release records, verification and recovery

Before schema change, identify the target, previous schema pair and release: exact Git revisions for each shipped component and migrations, Build IDs, source and dependency pins, build/toolchain inputs and renderer/configuration references needed to reproduce the installed behavior. Record these without secrets and retain or verify access to the payloads or reproducible inputs. Record the upgrade release too. With exclusive admission held, take a recoverable snapshot after the last permitted write. Link the snapshot receipt, target and prior release record; verify the snapshot by restoring it to isolated state before applying the upgrade. Refuse a receipt for the wrong database, prior release, revision or maintenance session. Keep credentials, private runtime data and backup payloads outside Git.

Verify target ledger and data invariants, migrated data, the selected compatible Builds and matching component protocols before reopening. Production checks under the fence must leave no user writes or outstanding work; use read-only checks and exercise write journeys on disposable/restored state. Reopening is a deliberate, recorded change in admission to the verified release. If anything fails before reopening, retry from the ledger under the fence, or restore the snapshot and matching previous Builds/configuration. Verify the restored release and absence of stale clients before reopening it.

After reopening, prefer repair forward. Before restoring an older snapshot, fence again, preserve the current database and other affected persistent state, and prove that all later accepted writes can be preserved and reapplied consistently; otherwise repair forward. A pre-upgrade snapshot by itself never authorizes discarding later writes. Report and retain recovery evidence including which release was reopened and where the write boundary fell.

### One backend, App and administration

One owner-only backend endpoint serves the App and backend CLI, with one installation settings scope and one listener set. The App can supervise the backend while open; CLI backend operations can acquire the same backend with the App closed and cannot start a second listener set. `arbol-trunk run` works directly with the App closed and uses the common schema and writer admission checks. Existing direct Vigor commands use the same installation configuration and admission even when they do not traverse the backend socket. Driver-only operations and installation health remain available during a database outage where independent; database operations distinguish unavailable, incompatible and maintenance refusals.

Bridge version 2 begins with the [installation greeting](../backend/01-the-bridge.md#single-database-amendment) instead of a Root record. It reports backend Build, schema compatibility and availability, maintenance state and capabilities without credentials or filesystem internals. Unsupported versions show a compatibility refusal before requests or subscriptions. The App/renderer/backend are activated as a compatible set; reconnect refreshes state and does not automatically retry non-idempotent actions. Remove the Root catalogue, current Root, Root routing, migration provenance and `chat.reimport` from active interfaces.

Elma and external open/shortcut routing address a chat UUID or workspace intent in the installation. No Root picker, Root title or stale copy action. Keep Draft protection, pending-send recovery, control for an accepted Exchange and selection of Trunk for the next Exchange, including Send Again. A changed choice affects only the new Exchange. During maintenance keep saved content and retained Draft state usable where possible, explain the refusal and do not imply a new Exchange started. Seqoya Lab is one window; it displays installation-wide subscriptions, Vigor history and administration using the same data source as the CLI. Do not manufacture reports before the first new collection.

### Chat identity and historical readers

For an Arbol chat, the Trunk passes the canonical lowercase, hyphenated chat UUID as `chatSessionId`, and passes `arbolChat: true` to Claude and Codex. These Drivers validate both fields before invoking their vendor tool and set only `ARBOL_CHAT` in the environment of that run. Absence of the marker keeps the old opaque continuity behavior and creates no Arbol identity. Any supplied value other than JSON `true`, invalid/missing UUID when marked, or presence of legacy `rootId` is invalid input for those two Drivers. Ignore inherited `ARBOL_CHAT` and `ARBOL_ROOT`; never export `ARBOL_ROOT`. Keep Driver continuity lookup and non-Arbol standalone IDs unchanged. Pi and MiMo receive the existing continuity field without the marker; background/small calls without a chat remain unmarked.

Forester's hooks and CLI use the same validated chat UUID for new Arbol attribution and the booking key `arbol:<uuid>`; tools still retain their native session identity where required for their Ledger events and cues. New Arbol ownership, edit checks and release resolve the same key, including when a tool also provides a native session ID; explicit CLI identity and standalone native sessions keep their existing behavior. Historical keys such as `arbol:<legacy-root>/<uuid>` are opaque recorded identities. Retain and resolve the exact key when reading historical bookings, history and Ledger; do not merge records just because their UUID suffix matches. Resolve open legacy bookings under the legacy runtime and its existing resolver before activating the new identity mode, not by renaming their owner. A legacy run is not reattributed to the new key. See FOR-2 and FOR-3.

### One-time cutover

1. In rehearsal, identify both existing databases and the proposed retained database (the currently active database by default). Inventory corresponding Builds and config, including safe connection and credential references, effective route/repository defaults, listeners and workspace/shortcut preferences, private file dependencies, Driver installations/sign-ins, pending Exchange files and live legacy Arbol bookings. Record explicit target identity and what will carry forward. Use the retained installation's effective settings as defaults; preserve differing legacy settings in the recovery record for explicit reconciliation. Do not carry over per-chat Drafts, prior Vigor data or historical chat state.
2. At cutover, confirm the actual target and previous release identities again. Enter maintenance for **both** legacy writer sets, including direct legacy launches, other retained backend/listeners, Vigor, accepted Trunks and legacy settlement. Because they do not know the new admission protocol, positively fence their old entry points and connections before reset; a new state flag alone is insufficient. Drain accepted work; settle pending files against their original databases. Inspect, preserve and account for any file that cannot be reconciled; do not proceed with unresolved accepted work. Release/close legacy bookings through Forester under their recorded ownership; unresolved live legacy ownership blocks cutover.
3. Take both final backups after legacy writes stop. Restore **each** into isolated state outside the live installation and verify database identity, schema, readable representative historical chat and Vigor data where present, and required associated file/configuration dependencies. Record both verified backup receipts and the previous release/configuration needed to resume. Both backups are the archive. Protect them and associated recovery material; do not add them to Git.
4. With the fence held and both receipts verified, clear only the confirmed retained target and initialize the new baseline there. Retire old launchers, listener jobs, settings selection and write credentials/paths that can still reach it. Verify empty chats, Exchanges, Drafts and Vigor history, no pending runtime work, one backend and matching Builds. Preserve Driver sign-ins and the reviewed installation configuration without restoring old chat state. Record the empty baseline before running any intentional write smoke journey. Reopen only after those gates and record that boundary.
5. Before reopening, recovery can restore both previous database states and their matching runtime/Builds/settings with new writers still fenced. After reopening, apply the no-loss rule above; the authorized empty start is a one-time transition and does not authorize throwing away subsequently accepted work.
